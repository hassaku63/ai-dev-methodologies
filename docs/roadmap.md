# ロードマップ

進め方の原則: 動いているリポジトリから抽出する。実際の導入先（または架空の例）で確かめながら、小さく広げる。

## 段階

| 段階 | やること | 終わりの条件 | 状態 |
| --- | --- | --- | --- |
| 0. 土台 | 目的、決定、作業の規則を文書にする | 文書だけで文脈を取り戻せる | 済み |
| 1. 規約と core | 導入先が守る規約（`docs/contract.md`）を定義する。`core` の plugin（導入、Issue の流れ、実装とレビューのサブエージェント、文書の鮮度）とマーケットプレイスの定義を作る | 空のリポジトリに導入して、検査が通る状態になる（`make test-adopt`） | 済み |
| 2. 逆輸入で確かめる | `hassaku63/chord-rambler` に導入し直した場合を、手書きの版と比べる | 差を説明できる。規約の不足を直してある | 未着手 |
| 3. 運用・管理 | 「調べて報告」の段階の部品を作る。読み取り専用の権限の設定、危険なコマンドを止めるフック、棚卸しと Finding のまとめの手順、記録の書式 | 架空の例のリポジトリで、棚卸しと Finding のまとめが一通りできる | 未着手 |
| 4. IaC | Terraform と CDK の検査、plan と diff の要約、反映の線 | 架空の例のリポジトリで使える | 未着手 |
| 5. 知識の索引と更新 | 鮮度つきの索引（プラクティス、標準）の使い方と検査、種になる項目。月次の報告のジョブ。手で変えたコピーの差分を示す手順の確かめ。Cursor と Codex 向けの出力 | 2 つ以上の導入先に更新を届けられる | 未着手 |

段階 3 と 4 は、会社のリポジトリを使えないので、架空の例を作って確かめる。実地での確認は所有者が行う。

## あとで検討すること

- このリポジトリの GitHub に、規約のラベル（`docs/contract.md`）を作る。作るまでは、Issue の流れは働かない。
- 「あとで検討すること」を `observation` の Issue に移し、この節をなくす（`docs/dev/docs-hygiene.md` の規約）。
- 役割の分担（指示書をファイルで渡す、実装に関わっていない目で確かめる、修正の回数に上限を置く）を、運用・管理の調査にどう当てるか。
- エージェントの失敗を、検査 → フックと権限 → `AGENTS.md` の順で固定先を選ぶ手順を、スキルにするか。
