# ロードマップ

進め方の原則: 動いているリポジトリから抽出する。実際の導入先（または架空の例）で確かめながら、小さく広げる。

## 段階

| 段階 | やること | 終わりの条件 | 状態 |
| --- | --- | --- | --- |
| 0. 土台 | 目的、決定、作業の規則を文書にする | 文書だけで文脈を取り戻せる | 済み |
| 1. 規約と core | 導入先が守る規約（パスとコマンド）を定義する。`core` の plugin（Issue の流れ、実装とレビューのサブエージェント、文書の鮮度、索引の使い方、導入の手順）とマーケットプレイスの定義を作る | 空のリポジトリに導入して、検査が通る状態になる | 未着手 |
| 2. 逆輸入で確かめる | `hassaku63/chord-rambler` に導入し直した場合を、手書きの版と比べる | 差を説明できる。規約の不足を直してある | 未着手（やるかどうかは所有者の判断待ち） |
| 3. 運用・管理 | 「調べて報告」の段階の部品を作る。読み取り専用の権限の設定、危険なコマンドを止めるフック、棚卸しと Finding のまとめの手順、記録の書式 | 架空の例のリポジトリで、棚卸しと Finding のまとめが一通りできる | 未着手 |
| 4. IaC | Terraform と CDK の検査、plan と diff の要約、反映の線 | 架空の例のリポジトリで使える | 未着手 |
| 5. 更新の仕組み | コピーしたものの版の記録と、更新のときの差分の提案。種になる索引の項目。Cursor と Codex 向けの出力 | 2 つ以上の導入先に更新を届けられる | 未着手 |

段階 3 と 4 は、会社のリポジトリを使えないので、架空の例を作って確かめる。実地での確認は所有者が行う。

## 所有者の判断を待っていること

- 段階 2 をやるか、省いて段階 3 に進むか。
- コピーしたものの更新の方式。案は、版を記録したファイルを置き、スキルが差分を読んで提案する方式（機械的な上書きより、導入先の手直しを壊しにくい）。段階 5 までに決める。

## あとで検討すること

- 役割の分担（指示書をファイルで渡す、実装に関わっていない目で確かめる、修正の回数に上限を置く）を、運用・管理の調査にどう当てるか。
- エージェントの失敗を、検査 → フックと権限 → `AGENTS.md` の順で固定先を選ぶ手順を、スキルにするか。
