# コンセプト

## 解決すること

個人や会社のコードベースとインフラ（主に AWS）を、開発・運用・保守する。対象のリポジトリは、扱う内容にばらつきがある。それぞれのリポジトリに、内容に合った AI 活用の枠組みを選んで導入し、導入したあとも更新を届けられるようにする。

このリポジトリは、そのための部品、導入と更新の仕組み、知識の索引を置く場所。規則そのものより、規則を選ぶ・入れる・保つ仕組みを持つ。

前提:

- 使う人は所有者 1 人。チームへの配布は考えない。
- 既定の道具は Claude Code。Cursor と Codex は補助的に対応する（ADR-0006）。
- 新規のリポジトリだけでなく、既存のリポジトリへのあとからの導入を対象にする。
- 高頻度の開発は要らない。安全に、少しずつエージェントに任せる範囲を広げる。

## 導入先の種類

| 系統 | 例 | エージェントに求めること |
| --- | --- | --- |
| アプリケーション | ECS や Lambda で動くもの、CLI として実行するもの | 設計、実装、レビュー、検査を通すこと |
| IaC | CDK、Terraform | 変更の計画、plan や diff の要約、検査を通すこと |
| 運用・管理 | AWS のインフラの管理を git のリポジトリで記録・実施するもの | 下の「運用・管理のリポジトリ」 |

1 つのリポジトリが複数の系統に当たることがある。

### 運用・管理のリポジトリ

コードを書く場所ではなく、調査の手順と結果を記録する作業場。主にやること:

- `aws` の CLI や `gh` などで、インフラの構成（ネットワーク、インスタンスなど）と問題を取得する。
- 取得したものを棚卸しして整理する。
- Security Hub の Finding などを、稼働しているアプリケーションの単位などでまとめる。

目的は、所有者がアクションを取りやすくなること。成果物は、次に何をすべきかが分かる形の記録。

## 配り方

このリポジトリを、個人用の Claude Code のマーケットプレイスにする（ADR-0002）。配るものは 3 種類に分ける（ADR-0003）。

| 種類 | 配り方 | 例 |
| --- | --- | --- |
| 手順（どの導入先でも同じ） | plugin。更新が届く | Issue の選び方、企画の書き方、実装とレビューのサブエージェント、索引の使い方 |
| リポジトリに実在が要るもの | 導入のときにコピーし、導入した版を記録する | 検査のスクリプト、定期ジョブのワークフロー、Issue と PR のテンプレート |
| 導入先が所有するもの | 雛形だけを作り、中身は導入先で書く | `AGENTS.md`、ワークフローの文書、索引の項目 |

plugin の手順は、導入先の決まったパスとコマンドを前提にする。導入先が守るこの規約は、このリポジトリで定義する。

## 知識の索引

- このリポジトリには、公開してよい一般的な知識の、種になる項目だけを持つ。
- 索引の項目そのものは、導入先が所有する。確認日と、そのリポジトリとの接点は、導入先で持つ。
- 会社や組織に固有の知識の索引は、導入の途中か直後に、導入先のリポジトリの中で所有者自身が作るように、導入の手順で促す（ADR-0004）。

## 安全性

エージェントに任せる範囲は、導入先ごとに段階で選ぶ（ADR-0005）。本番環境への反映は、どの段階でも人間が行う。

| リポジトリ | 取り込むもの |
| --- | --- |
