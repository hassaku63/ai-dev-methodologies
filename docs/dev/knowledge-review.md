# 知識の目録の点検

`plugins/knowledge/catalog/` の項目が古くなったことに気づき、確かめ直す手順。決定は ADR-0011。導入先の対応表は、それぞれのリポジトリが持つ。目録を直すと、plugin の更新で導入先に届く。

## 月次の報告

`.github/workflows/knowledge-review.yml` が毎月 1 日に走る（手動でも走らせられる）。`scripts/knowledge-staleness.py` が次を調べ、指摘があれば `knowledge-review` ラベルの Issue を 1 つ作る。すでに開いていれば、本文を新しい報告で置き換える。

| 報告の節 | 意味 | すること |
| --- | --- | --- |
| 見直しの期限を過ぎた項目 | 確認日から、項目の間隔を過ぎた | 出どころを開き直す（下の手順） |
| 開けない出どころ | URL が開けない | 移った先を探して直す。無くなっていれば、別の一次情報に替えるか、項目を「外したもの」に移す |
| 別の場所へ移った出どころ | URL が別の場所へ転送される | 新しい URL に直す |
| 記録したコミットのあとに変わったソース | Git のソースのファイルが、記録したコミットより新しい | 報告の差分のリンクを開き、要点が変わったかを読む |
| 確かめられなかったソース | ファイルが移ったか、API が答えなかった | リポジトリを開いて、ファイルの今の場所を確かめる |
| 自動の確認を拒んだサイト | サイトが機械の取得を拒んだ | 参考。ほかの指摘と一緒に、人が開いて確かめる |

手元で走らせる:

```bash
python3 scripts/knowledge-staleness.py            # 全部（ネットワークが要る）
```

```bash
python3 scripts/knowledge-staleness.py --offline  # 期限だけ
```

## 項目を確かめ直す

1. 出どころを開く。Git のソースがあれば、記録したコミットとの差分を読む。
2. 「何を言っているか」「確からしさ」（標準では「何を決めているか」「状態」）が、今の出どころと合っているかを確かめる。
3. 合っていれば、確認日を今日にする。ソースのコミットも今のものに直す。
4. 合っていなければ、項目を直す。出どころが主張を取り下げていれば、項目を束の「外したもの」に移し、理由と ID を残す。ID は消さない（導入先の対応表が指している）。
5. 対象の版が変わったなら、「対象」を直す。導入先の検査が、古い版を使うリポジトリで項目を落とすようになる。

出どころを開かずに確認日だけを更新しない。開けなかったら、開けなかったことを PR に書いて、確認日はそのままにする。
