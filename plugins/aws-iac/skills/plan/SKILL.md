# plan

Terraform のコードの変更について、何が起きるかを所有者に示す。エージェントは計画までを行い、反映（`terraform apply`）は所有者が行う。

要約するのはスクリプト（このスキルのディレクトリの `summarize_plan.py`）。同じ plan からは同じ要約ができる。

## 手順

1. **誰として計画するかを確かめる。** `aws sts get-caller-identity` の結果（アカウントとロール）と、対象の環境（ワークスペース、ディレクトリ、変数のファイル）を所有者に示す。反映できる権限の認証情報で動いていたら、止めて所有者に伝える。
2. **変える前の状態を確かめる。** main に当たるブランチのコードで plan を走らせ、変更がないことを確かめる。変更があれば、コードと実際の環境がすでにずれている。作業を進めず、ずれの中身を所有者に示す。
3. **計画する。** 作業のブランチで走らせる。plan のファイルは `.terraform/` の下に置く（コミットされない場所。plan には秘密情報が入りうる）。
   ```bash
   terraform plan -out=.terraform/tfplan
   ```
   ```bash
   terraform show -json .terraform/tfplan > .terraform/tfplan.json
   ```
4. **要約する。**
   ```bash
   python3 <このスキルのディレクトリ>/summarize_plan.py .terraform/tfplan.json
   ```
5. **読み解きを足す。** 要約そのものは書き換えない。次を短く添える。
   - 「注意して見るもの」の 1 行ごとに、意図した変更かどうか。意図していない置き換えや削除があれば、原因の属性から、コードのどの変更が引き起こしたかを示す。
   - データを持つリソースの置き換えと削除は、失われるものと、避ける方法（属性を変えない、`moved` や `lifecycle` を使う、段階に分ける）を示す。
   - 「コードの外で変わっていたもの」があれば、この変更で巻き戻るものを示す。
   - 要約の件数と、Issue の受け入れ条件から期待する変更が合っているか。
6. **PR に載せる。** 要約と読み解きを PR の本文に書く。plan のファイルと JSON は載せない。リポジトリが公開されていたら、リソースの名前を載せてよいかを所有者に確かめる。
7. **止まる。** 反映はしない。反映のコマンドは、所有者への提案として書く。

## CDK のとき

`cdk diff` の出力はテキストで、要約のスクリプトはない。手順 1、2、6、7 は同じ。3〜5 の代わりに、次を行う。

1. スタックごとに `npx cdk diff <スタック>` を走らせる。出力は、コミットされない場所（`cdk.out/`）に置く。
2. 出力を読み、スタックごとに次を挙げる。数えた件数は、出力の行と照らして確かめる。
   - 削除されるリソース（行頭が `[-]`）。
   - 置き換えられるリソース（`replace`、`requires replacement`、`may be replaced` と出るもの）と、原因のプロパティ。
   - IAM のポリシーとセキュリティグループの変更（出力の先頭の表）。広がる権限と、開く通信を挙げる。
   - それ以外の変更と作成は、種類ごとの件数。
3. データを持つリソース（データベース、バケット、テーブル、ボリューム、キュー、ログのグループ、鍵）の削除と置き換えは、Terraform のときと同じく、失われるものと避ける方法を示す。
4. 読み解きはエージェントが行ったもので、機械の要約ではない。そう断って、削除と置き換えの行は、出力の該当する部分をそのまま添える。

## 守ること

- 反映しない。state を触らない（`import`、`state rm`、`force-unlock` など）。要るときは、所有者への提案として書く。
- 意図していない置き換えや削除を、説明なしに通さない。
- 属性の値を、会話・PR・Issue に写さない。
- plan が失敗したら、検査や設定を弱めて通さない。出力をそのまま示す。
