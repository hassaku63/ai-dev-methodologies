# adopt（aws-ops）

AWS のインフラを調べて記録するリポジトリに、`aws-ops` の置き場所を用意する。先に `core` を導入しておく（`AGENTS.md` と `make check` があること）。無ければ、`core` のスキル `adopt` を先に行う。

## 手順

1. **公開の範囲を確かめる。** 記録にはアカウント ID やリソースの名前が入る。リポジトリが公開されていたら、止めて所有者に伝える。
2. **置かれるものを見せる。** `bash <このスキルのディレクトリ>/adopt.sh --dry-run <リポジトリの最上位>` を走らせ、結果を所有者に示す。
3. **置く。** 作業用のブランチで、`--dry-run` を外して走らせる。
4. **plugin を有効にする。** `.claude/settings.json` の `enabledPlugins` に `aws-ops@ai-dev-methodologies` を足す。
5. **任せる範囲を書く。** `AGENTS.md` のガードレールに、次を足す。
   - エージェントは AWS を読み取るだけで、環境を変えない。変える操作は、記録に提案として書く。
   - 秘密情報の値と、保存されたデータの中身を読まない。
   - 取得したままの出力（`ops/raw/`）をコミットしない。
6. **認証情報を所有者に用意してもらう。** エージェントが使う AWS の認証情報は、読み取り専用にする（AWS の管理ポリシーなら `ReadOnlyAccess` か、より狭い `SecurityAudit` と `ViewOnlyAccess`）。フックは読み取りでない操作を止めるが、安全網で、防壁は認証情報の権限。用意の仕方を、所有者が `ops/README.md` に書く。エージェントは、認証情報を作らない・書き換えない。
7. **アプリケーションの単位を書いてもらう。** `ops/apps.json` は空で置かれる。所有者に、稼働しているアプリケーションの単位（名前と、タグや名前の接頭辞での見分け方）を尋ね、所有者が決めた内容で書く。分からなければ空のままにし、スキル `findings` の結果から案を作る。
8. **確かめる。** `make check` を通す。`aws sts get-caller-identity` で、読み取り専用の認証情報で動いていることを所有者と確かめる。
9. **報告する。** 置いたファイル、残した「（導入先で書く: …）」、所有者が決めること、を一覧にする。

## 守ること

- AWS を変える操作をしない。
- `ops/README.md` と `ops/apps.json` の中身（対象のアカウント、アプリケーションの単位）は、このリポジトリにだけ置く。ai-dev-methodologies には送らない。
