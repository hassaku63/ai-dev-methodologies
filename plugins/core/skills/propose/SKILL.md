# propose

観察（Issue、所有者の報告、調査の結果、自分で見つけた問題）を受けて、検討の結果を `.github/ISSUE_TEMPLATE/proposal.md` の形の Issue にする。使い方と判断の基準は `docs/dev/workflow.md` の「Issue の使い方」にある。

GitHub の操作は、そのセッションで使える道具（GitHub の MCP のツール、または `gh`）で行う。

## 手順

1. **元を集める。** 関係する `observation` の Issue と、会話での報告を挙げる。
2. **事実を確かめる。** 推測で書かない。コードや設定を読み、必要なら手元で再現する。事実と推測を分け、確かめ方を書く。
3. **問題を枠にはめる。** 設計に関わるなら ADR のテンプレート（文脈 → 決定 → 選択肢 → 結果）。リポジトリに固有の枠（設計の文書、規約）があれば、それを根拠にする。
4. **選択肢を 2 つ以上書く。** 採らない案にも、採らない理由を書く。
5. **推奨と、決めてほしいことを分ける。** 決めてほしいことは、所有者にしか決められないこと（優先、範囲、方針の選択）だけ。自分で決められることは推奨に入れる。
6. **スライス案を書く。** 1 PR = 1 スライス。受け入れ条件は確かめられる形で、サイズは S / M / L。PR の大きさの予算（`docs/dev/harness.md`）を超えそうなら分ける。
7. **Issue を作る。** ラベルは `proposal` と `needs-decision`（決めてほしいことがないなら `needs-decision` は付けない）。元になった観察の Issue は、本文で `refs #N` と挙げる。
8. **会話では 5 行以内で要約し、Issue へのリンクを示す。** 検討の本文を会話に繰り返さない。
9. **実装はしない。** 所有者が決めてから、スライスを `ready` の Issue にする（スキル `grill`）。

サブエージェントに任せる場合は、手順 2〜6 を渡し、「事実（出典つき）・選択肢・推奨・決めてほしいこと・スライス案」の下書きだけを返させる。Issue の作成と会話での要約は自分で行う。
