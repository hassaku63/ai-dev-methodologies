# adopt

今のリポジトリを、ai-dev-methodologies の規約（`AGENTS.md` を正典にする、検査を `make check` に集める、Issue と PR で作業を回す、文書を現在の状態に保つ）に合わせる。新規のリポジトリにも、既存のリポジトリにも使う。

ファイルを置くのはスクリプト、判断が要るところはこの手順で行う。スクリプトは、このスキルのディレクトリの `adopt.sh`。

## 手順

1. **調べる。** リポジトリを読み、次を把握する。分からないことだけを所有者に尋ねる。
   - 何のリポジトリか。アプリケーション、IaC（CDK、Terraform）、運用・管理（インフラの調査と記録）のどれに当たるか。複数に当たってよい。
   - すでにある指示書（`AGENTS.md`、`CLAUDE.md`、`.cursor/rules` など）、検査（`Makefile`、CI、lint の設定）、文書。
   - main に当たるブランチの名前。
2. **置かれるものを見せる。** `bash <このスキルのディレクトリ>/adopt.sh --dry-run <リポジトリの最上位>` を走らせ、結果を所有者に示す。`exists` と `kept` は、すでにあって触らないファイル。
3. **置く。** 作業用のブランチで、`--dry-run` を外して走らせる。
4. **すでにあったファイルを合わせる。** `exists` と `kept` の行ごとに、今あるファイルを読み、規約に足りないものだけを足す。置き換えない。
   - `Makefile`: `check` のターゲットがあり、`docs-check` を呼ぶ。`pr-size` のターゲット（置かれた `check-pr-size.sh` を `bash` で、比べる先の `PR_BASE` を渡して呼ぶ）がある。今ある検査（lint、テスト、ビルド）も `check` から呼ぶ。`Makefile` を使わない方針なら、`make check` に当たる 1 つのコマンドを所有者と決め、`AGENTS.md` に書く。
   - `AGENTS.md`: 今ある内容を残し、雛形（スキルのディレクトリの `assets/owned/AGENTS.md.tmpl`）の節のうち、無いものを足す。`CLAUDE.md` に規則が書いてあれば `AGENTS.md` に移し、`CLAUDE.md` は `@AGENTS.md` と Claude Code に固有の補足だけにする。
   - `.claude/settings.json`: 今ある設定を残し、`extraKnownMarketplaces` と `enabledPlugins` の項目を足す。
   - `.github/workflows/ci.yml`: 今ある CI に、`make check` を呼ぶ必須のジョブがあるようにする。PR のときに `make pr-size` を走らせる段も足す（雛形の `ci.yml` と同じ形）。
   - `docs/README.md`: `docs/` の文書を全部、Markdown のリンクで載せる。
   - `.gitignore`: `.claude/settings.local.json` と `__pycache__/` を足す。
5. **既定のブランチに合わせる。** 1 で調べた main に当たるブランチが `main` でなければ、作ったファイル（`Makefile` の `PR_BASE`、`.github/workflows/ci.yml` の `branches`、`AGENTS.md`、`docs/dev/workflow.md`）の `main` を、そのブランチの名前に直す。
6. **埋める。** 作ったファイルの「（導入先で書く: …）」を、リポジトリを読んで分かる範囲で埋める。推測で埋めない。読んでも分からないものは、所有者に尋ねるか、そのまま残して最後に一覧にする。
   - 今ある検査を `docs/dev/harness.md` に 1 行ずつ足す。
   - CI の雛形の「Set up the tools」に、検査が要る道具の導入を書く。
7. **任せる範囲を決める。** 所有者に、エージェントに任せる範囲を尋ね、`AGENTS.md` のガードレールに書く。調べて報告するだけ、コードを変えて PR を作る、インフラの変更を計画する（plan や diff まで）、開発環境に反映する、のどれか。本番環境への反映は、どれを選んでも人間が行う。
8. **このリポジトリに固有の知識を書いてもらう。** 所有者に、次を `docs/` に自分で書くよう促す。書く場所と見出しの案を示し、中身は所有者が決める。エージェントは、会話で聞いた内容を勝手に文書にしない。
   - 組織やチームの規則のうち、このリポジトリの作業に関わるもの。
   - 関係する文書やほかのリポジトリの場所。
   - 用語、環境の名前、連絡先。
   これらは導入先のリポジトリにだけ置く。ai-dev-methodologies には送らない。
9. **ラベルを用意する。** `observation`、`proposal`、`needs-decision`、`ready`、`priority:high` のうち無いものを、所有者に確かめてから作る。
10. **確かめる。** `make check` を通す。通らなければ、検査を弱めずに直す。
11. **報告する。** 置いたファイル、合わせたファイル、残した「（導入先で書く: …）」、所有者が決めること、を一覧にする。PR を開くかどうかは所有者に確かめる。

## 新しい版に合わせる

導入済みのリポジトリでは、手順 2 から行う。コピーするファイルの結果の読み方:

| 結果 | 意味 | すること |
| --- | --- | --- |
| `same` | 新しい版と同じ | なし |
| `updated` | 導入のあと手を加えていなかったので、新しい版に置き換えた | 差分を報告に書く |
| `edited` | 手を加えてあるが、新しい版はこのファイルを変えていない | なし（手を加えたことを報告に書く） |
| `kept` | 手を加えてあり（または導入の前からあり）、新しい版はこのファイルを変えている。置き換えていない | 下の手順 |

`kept` のファイルごとに、次を行う。

1. 次の行の `new version:` が、新しい版のファイルを指す。`diff -u <リポジトリのファイル> <新しい版のファイル>` で差分を取る。
2. 差分を、このリポジトリでの手直しの部分と、新しい版の変更の部分に分けて所有者に示す。新しい版の変更が何のためかは、ai-dev-methodologies の git log で分かる範囲で添える。
3. 所有者の答えに従う。
   - 新しい版を取る: 新しい版のファイルをそのまま写す。次に導入のスクリプトを走らせると `same` になり、以後は更新が届く。
   - 手直しを残す: 何もしない。そのファイルには、以後も更新が届かない（`kept` か `edited` と報告され続ける）。手直しが要る理由が導入先の事情なら、コピーするファイルではなく、導入先が所有するファイルに移す案を示す。
   - 両方を合わせる: 合わせた内容で書く。このときも、以後は `kept` か `edited` と報告される。

## 守ること

- 今ある規則や検査を消さない。食い違いは、所有者に示して決めてもらう。
- 検査を通すために、文書や検査を弱めない。
- `.agents/methodology.lock` を手で書き換えない。
