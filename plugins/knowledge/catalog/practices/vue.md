### 導ける値は computed にし、getter に副作用を書かない

| 欄 | 内容 |
| --- | --- |
| ID | `vue-computed-pure` |
| 出どころ | Vue の文書「Computed Properties」。https://vuejs.org/guide/essentials/computed |
| ソース | なし |
| 何を言っているか | ほかのリアクティブな値から導ける値は、computed で宣言する。computed は依存するリアクティブな値で結果をキャッシュし、依存が変わったときだけ計算し直す（メソッドは描画のたびに呼ばれる）。computed の getter は純粋な計算だけを行い、ほかの状態の書き換え、非同期の通信、DOM の操作をしない。状態の変化に応じた副作用は、watcher で行う。computed の戻り値を書き換えない。 |
| 確からしさ | 公式の推奨。誤用: computed の中で通信を始める、別の ref に書き込む。導ける値を、watch で別の ref に写して持つ。 |
| 当たるべき場面 | 部品に、ほかの状態から導く値を足すとき。watch で ref を更新する差分をレビューするとき。React の束の「描画から導ける値とイベントの処理に、Effect を使わない」の Vue での当てはめ。 |
| 判断の問い | この watch は、導ける値を別の状態に写しているだけではないか（computed にできないか）。computed の getter に、書き込み・通信・DOM の操作がないか。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |

### watcher での通信は、後片付けで古い要求を取り消す

| 欄 | 内容 |
| --- | --- |
| ID | `vue-watcher-cleanup` |
| 出どころ | Vue の文書「Watchers」の「Side Effect Cleanup」。https://vuejs.org/guide/essentials/watchers |
| ソース | なし |
| 何を言っているか | watcher の中で非同期の要求を出すと、要求が終わる前に監視する値が変わったとき、古い要求の結果で処理が走る。`onWatcherCleanup()` で、watcher が無効になり再び走る前に呼ばれる後片付けを登録し、古い要求を取り消す（`AbortController` など）。`onWatcherCleanup()` は v3.5 から使え、watcher の関数の同期の部分で呼ぶ（`await` のあとでは呼べない）。代わりに、watcher の関数の第 3 引数の後片付けの関数も使える。 |
| 確からしさ | 公式の文書。誤用: `await` のあとで `onWatcherCleanup()` を呼ぶ。後片付けを書かず、入力が速く変わったときに古い応答で表示を上書きする。 |
| 当たるべき場面 | 監視する値（ID、検索の語）に応じて通信する watcher を書く、レビューするとき。React の束の「Effect での通信は、後片付けで古い応答を捨てる」の Vue での当てはめ。 |
| 判断の問い | 監視する値が速く変わったとき、最後の要求の結果だけが反映されるか。後片付けの登録は、`await` より前にあるか。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |

### リアクティブな状態は、まず ref で宣言する

| 欄 | 内容 |
| --- | --- |
| ID | `vue-prefer-ref` |
| 出どころ | Vue の文書「Reactivity Fundamentals」の「Limitations of reactive()」。https://vuejs.org/guide/essentials/reactivity-fundamentals |
| ソース | なし |
| 何を言っているか | `reactive()` には制限がある。オブジェクト（配列、Map、Set を含む）にしか使えない。オブジェクトを丸ごと置き換えると、追跡が切れる。プリミティブの値を分割代入で取り出したり、関数に渡したりすると、追跡が切れる。これらの制限から、文書は `ref()` をリアクティブな状態を宣言する主な API として勧める。 |
| 確からしさ | 公式の推奨。誤用: `reactive` のオブジェクトから `const { count } = state` で取り出し、変わらない値を使い続ける。`state = reactive({...})` で置き換える。 |
| 当たるべき場面 | 部品や composable に状態を足すとき。リアクティブな値を分割代入する、関数に渡す差分をレビューするとき。 |
| 判断の問い | この状態は、`ref` で宣言できないか。`reactive` のオブジェクトを分割代入したり、丸ごと置き換えたりしていないか。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |

### props は親から子への一方向で、子は書き換えない

| 欄 | 内容 |
| --- | --- |
| ID | `vue-props-one-way` |
| 出どころ | Vue の文書「Props」の「One-Way Data Flow」。https://vuejs.org/guide/components/props |
| ソース | なし |
| 何を言っているか | props は親から子への一方向の結びつきで、親が変われば子に流れるが、逆には流れない。子が親の状態を誤って書き換え、データの流れが分かりにくくなるのを防ぐ。親が更新されるたびに、子の props は最新の値に置き換わる。子の中で props を書き換えない（Vue は警告を出す）。初期の値として使いたいなら子の状態に写し、変換したいなら computed にする。 |
| 確からしさ | 公式の文書。オブジェクトや配列の props は、結びつきは書き換えられないが、中の項目は書き換えられてしまう（Vue が防ぐのは費用が大きすぎる）。親と子が設計として密に結びついている場合を除き避け、ほとんどの場合はイベントで親に伝える、と文書は書く。誤用: 子の中で props のオブジェクトの項目を書き換え、親の状態を黙って変える。 |
| 当たるべき場面 | 子の部品が、受け取った値を変えたくなったとき。親と子で同じ状態を見たくなったとき。React の束の「状態は、重複させず、持つ部品を 1 つに決める」と合わせて引く。 |
| 判断の問い | 子の部品が、props（その中のオブジェクトや配列を含む）を書き換えていないか。変更は、イベントで親に伝えているか。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |

### 部品のテストは、公開の入口（props、イベント、スロット）と描画の結果で確かめる

| 欄 | 内容 |
| --- | --- |
| ID | `vue-test-public-interface` |
| 出どころ | Vue の文書「Testing」。https://vuejs.org/guide/scaling-up/testing |
| ソース | なし |
| 何を言っているか | 部品のテストは、部品が何をするかを確かめ、どうするかは確かめない。部品の公開の入口は、多くの場合、出すイベント、props、スロット。表示の論理は、渡した props とスロットに対する描画の結果で、振る舞いの論理は、利用者の操作に対する描画の更新と出すイベントで確かめる。単体テストの道具には、Vite と同じ設定と変換を使える Vitest を勧める。Vue に固有の単体テストの対象は、composable と部品。 |
| 確からしさ | 公式の推奨。部品のテストには、子をなるべく偽物にする白箱のものと、子も描画して統合を確かめる黒箱のものがあると説明する。誤用: 部品の内部の状態や、メソッドを直接呼んで確かめる。 |
| 当たるべき場面 | Vue の部品や composable のテストを書く、レビューするとき。テストの道具を選ぶとき。テストの束の「振る舞いを公開の入口から、状態で確かめる」の Vue での当てはめ。 |
| 判断の問い | このテストは、部品の内部（状態、メソッド）ではなく、props・イベント・スロットと描画の結果で確かめているか。部品の実装を変えずに内部の書き方だけを変えたら、テストは落ちるか（落ちるなら、実装の細部に結びついている）。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |

### Composition API と Options API は、1 つの部品で混ぜない

| 欄 | 内容 |
| --- | --- |
| ID | `vue-composition-vs-options` |
| 出どころ | Vue の文書「Composition API FAQ」。https://vuejs.org/guide/extras/composition-api-faq |
| ソース | なし |
| 何を言っているか | Options API の部品の `setup()` の中で、Composition API を使える。ただし、それを勧めるのは、Options API の既存のコードに、Composition API で書かれた新しい機能や外のライブラリを組み込む必要があるときだけ。Options API を非推奨にする予定はない。 |
| 確からしさ | 公式の文書。どちらを使うかは流儀が割れ、文書は両方を支える立場。誤用: 1 つの部品の中で、同じ状態を Options の `data` と `setup` の両方で持つ。 |
| 当たるべき場面 | 新しい部品をどちらの API で書くか決めるとき。Options API の既存のコードに、composable を使う機能を足すとき。 |
| 判断の問い | このリポジトリの部品は、どちらの API でそろえているか（規約や ADR はあるか）。1 つの部品で混ぜるなら、既存のコードに外の composable を組み込むためか。 |
| 対象 | `vue@3` |
| 確認 | 2026-11-15 / 間隔 365 日 |
