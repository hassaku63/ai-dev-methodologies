## 型と境界

### 検査の結果を型で返し、境界で一度だけ行う

| 欄 | 内容 |
| --- | --- |
| ID | `parse-dont-validate` |
| 出どころ | Alexis King「Parse, don't validate」。https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/ |
| ソース | `lexi-lambda/lexi-lambda.github.io:blog/posts/2019-11-05-parse-don-t-validate.md@9cb6e01` |
| 何を言っているか | 入力を検査して合否だけを返すと、分かったことが捨てられ、後ろの処理が同じ検査を繰り返す。検査の結果は、より精密な型の値として返す。これを外との境界で一度だけ行い、内側はその型を前提に書く。検査が処理の中に散ると、一部を処理したあとで不正が見つかり、状態が読めなくなる。 |
| 確からしさ | 一流派の主張（型で設計する立場）。著者は「厳格な要件ではなく、目指す理想」とし、型で表しにくい条件は、作る関数を 1 つに絞った型で代えてよいと書いている。誤用: 「起こり得ない」分岐 1 つを消すために、全体を作り替える。 |
| 当たるべき場面 | 利用者の入力、設定、外部の API の応答、保存したデータを内側に渡す入口を決めるとき。関数の引数の型を決めるとき。 |
| 判断の問い | 戻り値を使わない検査の関数（失敗を投げるだけ）を足していないか。境界より内側に、同じ条件の再検査や「ここには来ないはず」の分岐がないか。 |
| 対象 | なし |

## 抽象を足すか、足さないか

### 見込みの機能を作らない

| 欄 | 内容 |
| --- | --- |
| ID | `yagni` |
| 出どころ | Martin Fowler「Yagni」。https://martinfowler.com/bliki/Yagni.html |
| ソース | なし |
| 何を言っているか | 将来要ると見込んだ機能のコードは、要るときまで作らない。見込みは外れやすい。当たっても、ほかの機能が遅れ、複雑さが以後の変更を高くし、作り方が古くなって直す費用が出る。将来の柔軟性のための抽象化やパラメータ化も同じ扱い。 |
| 確からしさ | 広く共有された実務の知見。対象は、見込みの機能を支えるコードだけ。変更しやすくする作業（リファクタリング、テスト）は対象外で、複雑さを増やさない備えも対象外だと断っている。誤用: これを理由に、リファクタリングやテストを省く。 |
| 当たるべき場面 | 「あとで別の種類にも対応するから」と、引数・拡張点・設定の項目を先に足したくなったとき。 |
| 判断の問い | この差分で、今の Issue の受け入れ条件から使われない引数・分岐・項目はどれか。あとで足すときのリファクタリングを具体的に書けるか（書けて小さいなら、今は入れない）。 |
| 対象 | なし |

### 単純な設計の 4 つの規則

| 欄 | 内容 |
| --- | --- |
| ID | `beck-design-rules` |
| 出どころ | Martin Fowler「BeckDesignRules」（Kent Beck の規則の紹介）。https://martinfowler.com/bliki/BeckDesignRules.html |
| ソース | なし |
| 何を言っているか | 優先の順に、テストを通る、意図が読み取れる、重複がない、要素が最も少ない。最後の規則は、前の 3 つに役立たないものを除くという意味。将来の柔軟性のために足した要素は、実際には変更を難しくしがちだとする。 |
| 確からしさ | 広く共有された実務の知見。表現は著者ごとに違い、2 番目と 3 番目の順は重要ではないと Fowler は書いている。誤用: 「要素が最も少ない」を先頭に置き、意図を表す名前や関数まで削る。「誤った抽象は戻す」とは、重複の扱いで緊張がある。 |
| 当たるべき場面 | 設計の案を 2 つ見比べるとき。レビューで「これは要るか」を問うときの順番。 |
| 判断の問い | この差分で足した型・関数・ファイルのうち、テストを通す、意図を表す、重複を除く、のどれにも効いていないものはあるか。同じ知識（表、定義、設定の値）が 2 か所に書かれていないか。 |
| 対象 | なし |

## 変更の分け方とレビュー

### 小さな変更にし、構造と振る舞いを分ける

| 欄 | 内容 |
| --- | --- |
| ID | `small-changes` |
| 出どころ | Google Engineering Practices「Small CLs」。https://google.github.io/eng-practices/review/developer/small-cls.html 。Martin Fowler「Workflows of Refactoring」。https://martinfowler.com/articles/workflowsOfRefactoring/ |
| ソース | `google/eng-practices:review/developer/small-cls.md@3bb3ec2` |
| 何を言っているか | 変更は自己完結した 1 つのことに絞り、関連するテストを同じ変更に入れる。大きさは行数だけでなく、散らばるファイルの数でも決まる。リファクタリングは、機能の追加やバグの修正と別の変更にする。Fowler は、振る舞いを保つ変更（テストは通ったまま）と、機能を足す変更を同時にしないと言う。 |
| 確からしさ | 公式の推奨（Google）と、広く共有された実務の知見（Fowler）。大きさに固定の規則はなく、小さすぎて意味が読めない変更もよくない（新しい関数は、使う箇所と一緒に出す）。局所的な名前の直しは同居してよい。誤用: 行数だけで機械的に割り、単独では意味の分からない変更を出す。 |
| 当たるべき場面 | Issue を PR に切るとき。整理と、振る舞いを変える修正が、1 つの PR に混ざりそうなとき。 |
| 判断の問い | 差分を「振る舞いを変えない行」と「変える行」に分けられるか。前者だけなら、既存のテストが無変更で通るか。足した関数や型は、同じ PR の中で使われているか。 |
| 対象 | なし |
| 確認 | 2026-11-15 / 間隔 365 日 |
