# practices

開発の判断の前に当たる知見を引く。知見は 2 か所に分かれている。

| 置き場所 | 中身 |
| --- | --- |
| この plugin の `catalog/practices/` | 項目の本体（出どころ、何を言っているか、確からしさ、判断の問い、対象、確認）。どのリポジトリでも同じ |
| 作業中のリポジトリの `./docs/knowledge/practices.md` | 対応表。このリポジトリで使う項目の ID、このリポジトリでの場面、このプロジェクトの立場。このリポジトリだけの項目も持てる |

## 規則は 3 段で持つ

| 段 | 置き場所 | 中身 |
| --- | --- | --- |
| 機械の検査 | `make check`（`docs/dev/harness.md`） | lint・型・テストで強制できること |
| 規約 | `AGENTS.md`、`docs/` の文書、ADR | このプロジェクトが決めたこと |
| 索引 | 目録と対応表 | 決める前に当たる知見 |

上の段に上げられるものは上げる。項目が lint やテストで強制できるようになったら、対応表から外す。プロジェクトの立場が決まったら、規約を正とし、対応表の「このプロジェクトの立場」からそこを指す。

## 使い方

1. 決めようとしていることを 1 行で言う（例: 「この関数の重複をまとめるか」「この依存をテストで偽物に置き換えるか」）。
2. 作業中のリポジトリの `./docs/knowledge/practices.md` を読み、対応表の項目の ID から、この plugin の `catalog/practices/` の項目を引く。対応表の「このリポジトリでの場面」が「—」なら、目録の「当たるべき場面」で絞る。
3. 「判断の問い」を自分の案に当て、当たった項目の ID を PR に書く。「このプロジェクトの立場」が決まっていれば、それに従う。
4. 細部（数値、API の名前、手順）を根拠に使うときは、出どころを開いてから使う。目録は要点しか持たない。
5. 見直しの期限（確認日 + 間隔）を過ぎた項目を根拠に使うときは、先に出どころを開き直す。開けなければ、開けなかったことを PR に書く。
6. 対応表に無いが目録にある項目が当たりそうなら、引いてよい。対応表に足すかどうかは、所有者に示す（今の作業に混ぜない）。
7. どこにも見つからなければ、そう書いて進める。足すべき知見だと思ったら、観察の Issue にする。リポジトリに固有の知見ならそのリポジトリに、どこでも使える知見なら ai-dev-methodologies に。

作業中のリポジトリに `./docs/knowledge/practices.md` が無ければ、目録を直接引いてよい。そのときは、このプロジェクトの立場は「未定」として扱う。
